# Pokémon GO 對戰表

照 **2026-06-23 新版對戰系統**計算出招時機的逐回合模擬器。
全靜態、純前端、無後端、月費 0 元。

```bash
npm install
npm run data                # 抓最新資料、驗證（22 項檢查）、跟上一版比對變動
npm run changelog:backfill  # 一次性：回填真實的歷史變動日誌（約 36 MB、跑幾分鐘）
npm run verify              # 驗證模擬器（11 項）
npm run dev                 # http://localhost:4321
npm run build               # 產出 out/，直接丟任何靜態主機
```

**刻意不用 `PokeMiners/game_masters`** 當對戰數值的主源：2026-11-08 實測最近更新停在 2026-08-29，
上一次是 4 月。但它的**文字檔**是另一回事——那是遊戲裡真正會看到的中文字，
名字又幾乎不會改，所以中文名以它為主、PokeAPI 補新內容。

`npm run data` 會把 938 KB 原始檔瘦身成約 540 KB，同時寫一份到 `public/data/`，
前端用 `fetch` 載入——app shell 先畫出來，而且換資料不必重 build。

### 資料驗證（`npm run data` 會跑，任一項失敗就不產出檔案）

22 項檢查（20 項硬檢查 + 2 項提醒），包含結構、招式池參照完整性、屬性合法性、資料新鮮度，以及最關鍵的一項：

> **CP 引擎對帳** — 用 pvpoke 自己算好的 `defaultIVs` 回推 CP，
> 1619 隻在超級聯盟的 CP 必須全部 ≤1500。
> 這一項同時驗證了我們的 CPM 表、等級索引推論與 CP 公式。

中文化也是硬檢查，不是盡力而為：**84 種型態後綴**、**1619 隻寶可夢**、
**355 個招式**全部要查得到中文名，而且寶可夢與招式的中文名都不准互相撞名；
少一個就中止產出。新型態或新招式上線時會直接在這裡報錯，
不會默默在畫面上留一個英文名。

招式撞名那一項抓到過真的問題：超級專用招在遊戲裡叫 `Brave Bird+`，
數值卻跟原招差很多（威力 130/能量 55 vs 70/40），但中文都翻成「勇鳥猛攻」。
現在依序套三條規則區分——遊戲自己的 `＋`、屬性（氣場輪有惡與電兩種）、
`data/zh-forms.json` 的手工表（堅盾劍怪盾牌形態的快招）——還撞名就中止。

## 圖示

**圖片不放進這個 repo。** 那些是 Niantic 的美術資產，PokeMiners 只是從 APK 挖出來；
這裡只存識別碼（`go:pm487.fORIGIN`、`home:778`），執行時由 CDN 取，
所以這個專案不重新散布任何美術檔。來源與網址組法在
[`src/lib/icons.ts`](src/lib/icons.ts) 與 [`scripts/lib/icons.mjs`](scripts/lib/icons.mjs)，兩邊是同一組常數。

對照怎麼來的：GO 的檔名是 `pm{圖鑑編號}[.f{型態代碼}].icon.png`，
型態代碼是 Niantic 自己的英文列舉，大多數把 pvpoke 的後綴轉大寫就對得上
（`Therian` → `THERIAN`），對不上的收在 `data/icon-forms.json`
（`Alolan` → `ALOLA`、`Paldean` → `PALDEA`、Burmy 那種還要再掛一次 species 名）。
實際結果：

- **1584 隻**用 GO 自己的美術
- **35 隻** PokeMiners 沒有（含超級聯盟第 4 的謎擬Ｑ、第 5 的古月鳥），用 PokeAPI 的 Pokémon HOME 圖補
- **19 隻**退回本體圖——pvpoke 收了一些遊戲裡還沒實裝的超級型態，Niantic 根本還沒畫

**招式沒有自己的圖。** 遊戲裡招式就是用屬性圖示表示的（`Images/Combat` 裡確認過沒有招式美術），
所以招式一律顯示它的屬性圖示。

**不要用 jsDelivr。** jsDelivr 對整個 repo 有 50 MB 上限，`pogo_assets` 遠遠超過，
會零星回 403「Package size exceeded」——而且已經被它快取的照樣 200，
所以隨便抽幾張測是測不出來的（這就是抽驗要抽 60 張的原因）。
現在走 `statically.io`，載入失敗時前端會自己退回 `raw.githubusercontent.com`。

## 每日變動日誌

招式平衡調整是輸球的隱形原因：一招威力 +10、能量 −5，整個聯盟的對位就換一輪，
官方不會發公告。`npm run data` 每次都會跟上一版比對，把差異記進 `data/changelog.json`：

```
2026-09-01  Merge from master
  招式調整 8 項
    ◆ 空氣利刃  威力 45 → 60、能量需求 35 → 40、觸發機率 0.3 → 0.125
        影響主流：鋼鎧鴉（高級 #2）、鋼鎧鴉（暗影）（高級 #4）
    ◆ 泰山壓頂  威力 55 → 65、能量需求 35 → 40
        影響主流：卡比獸（暗影）（高級 #3）、卡比獸（高級 #13）、過動猿（超級 #26）
```

比對的項目：招式的威力／能量／回合數／能力變化、寶可夢的三圍與屬性、
**招式池增減**、新上線與下架、以及排名進出榜。
每一條招式調整都會標出「現在的主流裡誰會這招、排第幾」，
所以看得出來這次改動實際會打到誰。

幾個刻意的設計：

- **不另外存快照。** 上一版就是上一次寫出去的 `data/gamemaster.json` 自己。
- **招式全部出貨，不只「有寶可夢學得會」的那些。** pvpoke 常在寶可夢上線前
  就先把新招加進來，那正是最值得提早知道的變動（多出的 33 個招式約 4 KB）。
- **排名變動算次要訊號。** 資料源每次重算排名都會出一版，
  只有排名動的版本標成「沒有影響對戰的變動」，介面預設收起來。
- **`npm run changelog:backfill` 會回填真實歷史**：
  逐個抓 pvpoke 歷史上每一版 `gamemaster.min.json` 來比對，
  所以第一天就有紀錄可看，不是空的。

部署在 Cloudflare（免費方案）。從 Git 建專案現在走的是 **Workers Builds**，
部署指令固定 `npx wrangler deploy`，所以 repo 裡要有 `wrangler.jsonc`：
純靜態站不設 `main`，只指定 `assets.directory` 為 `out`，
Cloudflare 就直接把它當網站內容送出去。少了這個檔，Build 會過但 Deploying 會失敗。
`wrangler.jsonc` 裡的 `name` 必須和 Cloudflare 上那個 Worker 同名。
`.node-version` 指定 Node 22，不依賴建置映像的預設值（wrangler 4 也要求 Node ≥22）。

`.github/workflows/daily-data.yml` 是每天跑一次的排程。推上 GitHub 之後要做兩件事：

1. Settings → Actions → General → Workflow permissions 改成 **Read and write**
2. 把 repo 接到 Cloudflare Pages（或任何跟著 push 自動部署的靜態主機）

硬檢查失敗時那個 job 會紅燈而且**不會 commit**——寧可停在舊資料，也不要推半套上線。

## 對戰規則（為什麼要重寫）

Niantic 在 2026-06-23 重寫了 PvP 對戰系統，舊系統在 2026-08-30 世界賽後永久退役。
網路上大量攻略是改版前的，**出招時機的結論已經不成立**。

`src/lib/battle.ts` 照[官方公告](https://pokemongo.com/news/pvp-updates2026)實作五條規則：

1. 傷害與能量在**回合結束**結算 → 同回合的 1 回合快招會平手，雙方都生效。
2. 交換永遠先於傷害結算。
3. 快速交換 1 回合、強制交換 0 回合、大招結束時的交換 0 回合。
4. **大招在按下的下一回合才發動**（舊系統立刻發動，這條差最多）。
5. 大招的傷害與能力變化一定在 leak 進來的快招之前結算；
   sneak 快招只能發生在大招被按下的那一回合。

## 模擬器驗證（`npm run verify`）

**A. 規則單元測試 — 10 項，必須全過。**
逐條驗證上面五條規則、CMP 先手、第一發大招的回合公式，
以及傷害公式與一份獨立重寫的實作逐筆對帳（200 組，0 組不符）。

**B. 對 pvpoke 官方對位結果的外部對帳。**
拿 pvpoke 排名裡的 `matchups` / `counters` 當標準答案，
完全照它的 `rankingScenarios`（leads／closers／switches／chargers／attackers）跑五種情境平均，
比對勝負方向：**800 組中 637 組一致（79.6%）**。

### 已知落差

傷害、能量、回合時序是**精確計算**；落差來自**出招決策**。
pvpoke 的 `ActionLogic` 是 1294 行的 DP 搜尋，本專案只移植了三段關鍵啟發式
（生存檢查、誘餌捷徑、簡化版 DP）與完整的 `wouldShield`。
另外 Mimikyu 之類有特殊型態機制的寶可夢也還沒處理。

所以：**時間軸上的回合數、能量、傷害可以信；整體勝負預測當參考。**

## 六個分頁

網址的 `#hash` 就是分頁，連結可以直接分享到指定頁
（`#pokemon`／`#types`／`#moves`／`#team`／`#sim`／`#box`）。沒帶 hash 就開第一個分頁。
分頁依序是 寶可夢、屬性、招式、隊伍、對戰模擬、箱子。

### 對戰模擬（`#sim`）
兩隻對位的逐回合推演，見下面「對戰規則」與「模擬器驗證」。

上面是**播放器**：播放／暫停／單步／×1 ×2 ×4，拖得動的時間軸，
軸上的點是大招發動的回合。看得到 HP、能量、護盾、能力階級隨回合推進——
逐回合表格看得到每一步，但看不出推進感，播放器就是把同一份資料當成一場比賽播出來。
資料完全一樣，只是換個看法。下面的逐回合明細可以收合。

**逐回合明細是一張表**：時間、能量、血量各自占一欄，數字位數變了只撐開那一欄。
我方的招式永遠從同一個位置開始、對手的永遠在同一個位置結束（那一欄靠右），
所以兩邊都對得齊，招式也各自貼著自己的血量能量，中間的空白就是兩邊的分界。
能量擺在最外側、兩邊對稱。

會自己上下捲的大區塊（逐回合明細、留意招式）收窄到 880px 並置中——
整排撐滿的話，滑鼠放在上面滾輪只捲得動區塊內部，整頁反而捲不動；
兩邊留白就有地方可以捲整頁。對戰模擬整頁跟著同一個寬度，上下才對得起來。
窄螢幕先把血量那兩欄收起來。護盾、能量、大招記號都用跟寶可夢表同一組 SVG 圖示，
不用 emoji——emoji 的字寬與基線跟著系統字體跑，對不齊。

### 招式（`#moves`）
快招與大招看的是不同指標，所以分開顯示欄位：

- 快招：**Dpt**（每回合傷害 = 威力 ÷ 回合數）、**Ept**（每回合能量 = 能量獲得 ÷ 回合數）
- 大招：**Dpe**（每點能量的傷害 = 威力 ÷ 能量）、能力變化與觸發機率

招式清單與選單裡的數值固定排成「威力 → 能量 → 時間 → 比值」：
先看打多痛、再看多貴、再看要等多久，最後才是算出來的比值。
威力用爆炸圖示、能量用閃電圖示（「力」「⚡」各佔一格字寬卻只是標籤），
回合數直接換算成秒——遊戲裡感覺得到的是時間不是回合。
大招的能力變化寫成「自 攻-2」「敵 防-1」。

**打擊計算**在表的上面：左邊選一組防守屬性（不選就是 ×1），右邊從下面的招式表
點任一列加進來，最多三招。算的是**有效威力** ＝ 威力 × 倍率（本系再 ×1.2），
「能量效率」欄是大招的每點能量；快招沒有能量成本，那一格看的是每回合。

只算到有效威力就停：再往下的實際傷害要看攻守雙方的攻擊與防禦，那是對位的事
（模擬器在做），不是「這一招打這組屬性有多痛」要回答的。
本系加成逐招自己開——三招的屬性不一樣，攻方是不是本系也就不一樣，
一個全域開關會把三招一起算錯。

### 寶可夢（`#pokemon`）
三圍是**在那個聯盟的實戰值**——照 pvpoke 建議的等級與 IV 算出來的，不是種族值，
所以換聯盟整張表的數字都會變。耐久 = 防禦 × HP。

點一列展開單隻解析：

卡片上半分兩欄，左四右六：左邊是「牠是誰」（頭像、名字、屬性、名次、定位標籤），
右邊是「牠怕什麼」（屬性克制）。名次貼齊頭像下緣，所以它跟屬性之間自然留出一段距離。
右上角的 × 用絕對定位，不佔版位也就推不動頭像與名字；克制表往下讓 24px 給它。
卡片擠到一半寬（兩隻並排）或手機時，所有區塊都整排撐滿，由上到下是
**寶可夢 → 能力數值 → 屬性 → 招式**——窄畫面擺不下兩欄，硬排只會兩邊都半殘。
這時 × 改成由名字自己留出右邊的空間。

四塊分屬兩個容器，`order` 排不過容器的邊界，所以窄版讓這兩層
`display: contents` 整個讓開，四塊直接變成卡片的 flex 子項再排序。
卡片因此**永遠**是直排 flex——`@container` 的規則只套得到容器的子孫、
套不到容器自己，`display` 與 `gap` 寫在 query 裡不會生效。

- **屬性克制**：十八格一次攤開，一格同時講兩件事，用兩種編碼分開
  - **底色與記號**＝這隻挨那個屬性的倍率（防守面，永遠在）。
    被剋畫爆炸、抵抗畫盾牌，一級一個、兩級兩個；
    格子裡不寫倍率——十八個 ×1.00、×0.63 排在一起只會互相干擾，
    數字改放在**標題同一行最右邊的圖例**上講一次，而且只列這張表真的出現的那幾段
    （精確值像 ×0.391 留在滑過格子的 tooltip 裡）
  - **外框**＝滑過或點右下招式清單的那一招，打那個屬性的倍率（攻擊面，跟著招式走）。
    選取 2px、滑過 3px；外框用 `outline` 不是 `border`，outline 不占位置，
    粗細變化不會讓十八格跟著位移
  - 兩面本來就是獨立的兩件事，用切換會看不到關係。例如謎擬Q 的幽靈格
    同時是橘底（挨幽靈 ×1.60）加橘框（牠的幽靈招打幽靈 ×1.60）——「牠痛我、我也痛牠」
  - 兩面共用同一套顏色（見下面「配色」），因為顏色講的是倍率大小，
    不是「對你好不好」；換個方向看還是同一個意思
  - 屬性名一律灰色，訊號放在底色與記號上
  - 這一塊沒有標題——它就擺在寶可夢旁邊，十八個屬性圖示自己說得清楚是什麼。
    圖例擺在格子底下、整排靠右；選了招式時「外框為招式倍率」接在圖例左邊
- **推薦招式直接在招式清單裡放大**，不另外拉一條出來講同一件事
- **能力數值（五軸雷達圖）**：攻擊／耐久／爆發／充能／快攻。
  軸上寫**真實數值**，顏色是它在同聯盟的強弱段，位置是百分位——
  數字回答「多少」、顏色回答「算強還算弱」、位置回答「贏過多少人」。
  只給百分位看不出 121.0 是多少，只給數字又沒感覺，所以三個一起給。
  五個軸單位不同（攻擊 120 跟 DPE 2.0 沒得比），只有百分位放得進同一張圖。
  - **防禦與 HP 合成「耐久」（相乘）而不是各站一軸**：這兩個在對戰裡從來不是
    分開用的，防高血薄跟防薄血高是同一件事，兩軸分開只會讓偏科的形狀看起來比實際誇張。
    拆開的值寫在耐久軸底下那一行小字（`防 151.9 × HP 138`）
  - 形狀的底色是灰的（形狀本身不帶訊息），頂點塗自己那一段的顏色、跟軸上的數字同色，
    連線走漸層把頂點串起來
  - CP 掛在「能力數值」標題旁邊，不佔軸——它是等級與 IV 的結果，不是一項能力
  - 同時開兩張卡時，各自把對方疊成虛線，直接比形狀
- **定位標籤**：肉盾、出招快、誘餌好用之類，每個配一個小圖，
  滑過或點一下看判斷依據（就寫在標籤正下方）。
  **依據的招式不在推薦組合裡的標籤會轉灰**——標籤是拿「學得會的全部招式」算的，
  但你實際會帶的是推薦那組。例如「誘餌好用」靠的是最便宜與最貴那兩招，
  兩招不一定都在推薦裡；灰色表示它說的是潛力，不是你現在這組的實力
- **列表只列攻擊與耐久**，防禦與 HP 不單獨開欄（同上：分開看沒有意義）。
  兩欄下面都有細長條，以目前這張表最高的那個當 100%，
  用長度比例顯示，每 20% 換一個顏色（紅→橙→黃→黃綠→綠）——
  數字要一個一個比，長度與顏色掃一眼就知道誰偏科
- **「擅長抵抗」篩選**：選一個屬性，只留挨那個屬性的招式會減傷的
  （×0.63、×0.39，免疫也算在內）。換人上場擋對手主力時用這個找人，
  比自己背相剋表快

列表的寶可夢圖與屬性圖示都放大；單屬性置中，雙屬性左下右上微微疊著、
第一屬性壓在上面——兩個圖示排排站會讀成兩件事，疊起來才像同一隻的一組屬性。

卡片放在表格上面、不在捲動區裡，所以翻表時不會跟著跑掉；最多同時放兩隻比較，
點第三隻會擠掉先選的那一隻。判斷依據不用原生 `title`——桌機要停一秒、手機完全不跳，
等於把算式藏起來；改成寫在標籤下面那一行。

標籤門檻不是寫死的數字，是**跟同聯盟上榜的那一批比**算出來的分位數——
寫死「耐久大於 18000 算肉盾」換個聯盟就不成立。每個標籤都寫出實際數值與門檻，
所以結論可以自己驗。

### 屬性分桶不可以直接比大小

`MULT` 裡的常數帶著 Niantic 的浮點尾數，而且**不能四捨五入掉**（傷害 `floor` 之後的結果會變）。
拿它們去比大小會錯，一律走 `effBucket()`：

| 寫法 | 實際值 | 後果 |
|---|---|---|
| `mult > 1` | `1.6…×0.625 = 1.0000000149` | 「被剋一次又抵抗一次」的中性組合被當成被剋 |
| `mult > 1.6` | `SUPER_EFFECTIVE = 1.60000002384…` | 單純被剋被當成雙重被剋 |
| `mult > 1.2` | `STAB = 1.2000000476…` | 每一個「本系打中性」都被當成剋制 |

三個都踩過。第一個讓勾魂眼（幽靈／惡）多出蟲、幽靈、惡三個弱點，巨沼怪（水／地面）
多出水、冰；全部 2754 組雙屬性組合裡有 187 組被分錯桶。

`npm run verify` 的 C 區守著這件事：雙屬性的桶必須等於兩個單屬性的桶相加
（單屬性不經過乘法，沒有尾數問題，可以當獨立的一份對照），再加上手算得出來的實例。

### 屬性（`#types`）
選一到兩種屬性，上面出這個組合挨十八種屬性的倍率，下面列出帶這個組合的寶可夢。

十八格不照圖鑑順序排，照抵抗程度分五欄（雙重被剋→被剋→普通→抵抗→雙重抵抗）。
欄位固定在同一個位置，換一個組合用掃的就知道第一欄多了誰、第五欄少了誰。
手機上五欄並排只剩兩個字的寬度，改成三排：兩個極端（雙重被剋／雙重抵抗）在最上面，
被剋／抵抗在中間，「普通」整排放最下面。

倍率寫在欄標題不是寫在每一格，因為同一桶裡的倍率是固定的：被剋一定 ×1.60、
抵抗一定 ×0.63（抵抗一次，或原作免疫再被剋一次，兩條路都剛好是 0.625）。
唯一會變的是雙重抵抗——抵抗兩次 ×0.39、原作免疫再抵抗 ×0.24、免疫兩次 ×0.15。
常態的 ×0.39 一樣寫在欄標題上，只有真的跑出 ×0.24、×0.15 的那幾格才自己報數；
整欄都是特例時標題留白，改由每一格報。GO 沒有免疫，原作的免疫在這裡一律折成 ×0.39。

`只看完全相同` 打開是「屬性組合完全一樣」，關掉是「帶有其中任一屬性」。
單選一種屬性時這個開關差很多：開著只有純該屬性的，關掉是所有帶該屬性的。

### 隊伍（`#team`）
放三隻進去，回答「對手可能帶什麼招、我被什麼剋」。三塊分析各有各的來源，精確度不一樣：

| 區塊 | 我方／對手 | 資料來源 | 可信度 |
|---|---|---|---|
| 屬性克制 | 同名 | 屬性相剋表 | **精確**，純計算 |
| 留意招式 | 建議招式 | pvpoke 統計的**實際使用率** | 觀測值，不是「牠學得會什麼」 |
| 較難應對 | 建議使用 | 本專案的模擬器現場跑 | 參考，出招決策是簡化版 |

「留意招式」刻意用使用率而不是可學招式池：學得會但沒人帶的招列出來只會洗版。
預設**照威脅排**（先看剋你幾隻）而不是照遇到率排，否則最常見但打不痛你的招會塞滿前面；
這兩顆排序鈕放在標題同一排，它們是那張表的開關，掉到別的地方就看不出在管誰。

「較難應對」是拿前 30／50／100 名主流逐一對過你那三隻，照你實際選的招式與護盾。
一場模擬約 0.3 ms，所以 100 名 × 3 隻只要 ~90 ms，可以邊調邊看。

### 箱子（`#box`）

其他分頁算的都是「理論上最好的那個個體」，但你手上就是沒有那一隻。
這一頁存你**實際擁有**的等級、IV 與招式，反制查詢只拿這些去跑。

- 加進來的方式有兩個：這一頁搜尋後填等級與 IV，或是在寶可夢表按每一列右邊的 ＋
  （先帶該聯盟的建議個體當起點，再改成自己的）
- IV 欄位直接貼檢定結果就好，`15/14/13`、`15 14 13`、`15,14,13` 都讀得出來
- **超過聯盟 CP 上限的會灰掉並排除在反制查詢外**——遊戲裡不能把寶可夢降級，
  所以一隻 15/15/15 的美錄梅塔（CP 1594）在超級聯盟就是進不去，列出來只會誤導
- **反制查詢**：選一隻對手，0／1／2 盾各跑一場。
  兩邊同盾數，因為盾數差一個本來就會翻盤，混著比看不出是誰的功勞

箱子存在這台裝置的 `localStorage`，不上傳任何東西——這是純靜態網站，沒有後端可以存，
也不該為了這個功能去要一組帳號。代價是換裝置要重建。
讀寫都包在 try/catch 裡，無痕視窗或關掉網站資料時會當成空箱子，不會讓整頁掛掉。

有了箱子之後，**變動日誌會標出「打到你箱子裡的 N 隻」**並可以只看那幾版。
判斷標準是「你這隻學得會那一招」而不是「你現在剛好帶著它」——帶不帶可以改，學不學得會不能。

## 介面

### 配色

米白底，只有一套，不跟著系統的深淺色切換——克制表那四個顏色要在固定的底色上才站得住。
展開／收合的三角箭頭一律用 SVG 不用 `▸` 這種字元：三角形字元只佔 em 框的一小塊，
字級調到跟旁邊的字一樣大，看起來還是小一號。

**形狀就是「能不能按」的提示**：按鈕、輸入框、選單一律方形圓角（8px），
純標示、按不下去的東西（屬性膠囊、名次、克制表的格子、推薦徽章）一律膠囊。
整站只有這兩種形狀。

三層由深到淺：最底的頁面背景（`--bg`）、卡片（`--surface`）、控制項（`--surface-2`）。
按鈕、輸入框、標籤、克制表的格子是**最亮**的那一層——它們是要被讀的東西，
擺在最亮的底上文字對比最好（本文 14.7、次要文字 5.6）；卡片只是把它們圈在一起的容器。

倍率分四段，四個顏色，整個平台同一套（寶可夢表的解析卡、屬性表、對戰組合表）：

| 倍率 | 顏色 |
|---|---|
| 雙重被剋 ×2.56 | 紅 |
| 被剋 ×1.60 | 橘黃 |
| 抵抗 ×0.63 | 綠 |
| 雙重抵抗 ×0.39 | 藍 |
| 再往下的特殊倍率 ×0.24、×0.15 | 藍紫 |

唯一來源是 `typeChart.ts` 的 `effClass()`，CSS 變數是
`--ef-w2`／`--ef-w1`／`--ef-r1`／`--ef-r2`／`--ef-r3`。
最後那一段是從雙重抵抗裡再切出來的：`effBucket` 把 ×0.39、×0.24、×0.15 都歸在 −2，
但實際差了兩倍半，門檻取 0.3（夾在 0.39 與 0.24 中間，浮點尾數跨不過去）。

這四個顏色講的是**倍率大小**，不是「對你好不好」，所以挨打與出手共用同一套，
對戰組合表切我方／對手也不翻面——同一個 ×0.39 在哪一張表都是藍的，不用靠記憶讀。
「對你好不好」是另一組（`--foe` 紅／`--good` 綠），只用在勝負與「剋你幾隻」那種結果欄。

橘黃在米白上的對比約 3.2——再壓深就變土色、看起來反而更不明顯，所以強度改用底色補
（屬性表的被剋欄有 17% 的橘底）。倍率本身就印在格子裡、屬性表的欄標題也寫了桶名，
顏色是重複編碼而不是唯一資訊（記號還分爆炸與盾牌兩種形狀，不看顏色也分得出來），
所以這一段沒有拿對比去換視覺強度的問題。

雙重那兩段的底色（24%／22%）壓得過單重那兩段（17%／15%），
加上圖示與字級本來就大一圈，階層不會倒過來。

- 畫面全中文（寶可夢、招式、型態、屬性都是 GO 遊戲內的用字）；
  搜尋框中英文都吃得下，查國外攻略時打英文比較快
- 寶可夢圖示出現在選單、面板與對位；招式與屬性用屬性圖示，
  時間軸上一眼就看得出這一回合丟的是什麼屬性
- 頁尾一條「資料變動」，收起來時用一句話交代最近一次有影響的改動，
  展開是完整日誌，預設只列有影響對戰的版本（放最下面是因為它是背景資訊，
  不是每次開站都要看的東西）
- 三個聯盟切換，預設招式直接用 pvpoke 推薦的那一組；招式不分聯盟，
  按鈕留著變暗（整排收掉會讓下面的內容往上跳一層）。
  手機上聯盟自己一排放在分頁上面靠右，分頁排成三欄兩列、整排撐滿
- 設定面板的版型是「圖片在左，名字那一欄在右」：標題 → 選單 → 屬性。
  選單旁邊就是大圖，所以選完只留名字，不再放一次小圖（選單的選項仍然有圖）。
  屬性那一排用 `margin-top: auto` 頂到底，下緣剛好對齊圖片的下緣
- 屬性篩選與招式選單都是自訂選單不是原生 `select`——原生 `option` 裡放不了圖片，
  而招式與屬性在遊戲裡就是靠圖示認的，只剩文字會慢一拍
- 表格裡的數字一律等寬對齊：`.tbl td` 全部吃 `tabular-nums`（少掛一個 class 就整欄參差），
  小數位數固定（pvpoke 的分數有 29／300 是整數，照原樣印會少一位），
  等級一律一位小數，IV 的個位數補一個數字寬的空白（`U+2007`）
- 兩側各自選寶可夢／快招／兩個大招／護盾
- 「最佳出招」vs「能量一滿就丟」可以切換對照，看得出誘餌的價值
- 逐回合時間軸：每回合雙方做了什麼、累積能量、剩餘 HP，
  大招發動回合highlight，並標出「最快第幾回合按得下第一發大招」
